# Plan 007：光流条纹问题迭代调试计划

## 1. 当前现象（2026-02-23）

- **已确认**：flow 数据对运动有响应
  - 挥手时出现黑线，随挥手频率闪动
  - 延迟低，说明 flow → 渲染 → INVOKE 链路正常
- **待解决**：画面为垂直黑白条纹，而非期望的「亮=运动区域」灰度图
- **JPEG_Q_HIGH / JPEG_Q_BEST** 均已尝试，条纹未消失，故主要怀疑非 JPEG 压缩质量导致

---

## 2. 问题定位假设（按优先级）

### H1：flow tensor 空间布局/周期性与条纹对齐

- **假设**：模型输出的 flow 具有列向或行向周期性（如 8/16 像素），导致条纹
- **验证**：串口输出每帧 flow 的列均值曲线（或每隔 N 列采样），检查是否有周期
- **改动**：在 `ob_log_infer_line` 或新增低频调试中，输出 `col_mean[0..W-1]` 的简化版（如每 8 列一个值）

### H2：per-frame max_mag 归一化导致静态噪声被放大

- **假设**：静态时 max_mag 来自量化噪声，归一化后整幅图接近均匀灰；有运动时 max_mag 突增，相对关系变化，可能凸显模型固有的行列结构
- **验证**：改用固定 scale 归一化（如 mag 直接映射到 0–255，用固定阈值截断），观察条纹是否变化
- **改动**：`flow_render_to_gray` 增加模式：固定 scale（mag * k + offset）vs 当前 per-frame max 归一化

### H3：flow tensor 内存布局与读取 stride 不匹配

- **假设**：若模型输出为 NCHW（先整幅 dx，再整幅 dy），当前 stride=2 的 NHWC 读法会错位，产生条纹
- **验证**：查 TFLite 输出 dims 与 layout；或尝试 NCHW 读法对比
- **改动**：按 `out_dims` 判断 layout，分支读取

### H4：JPEG addMCU 的 (x,y) 坐标语义

- **假设**：`jpe.x`, `jpe.y` 若为 MCU 索引而非像素坐标，`gray[jpe.x + jpe.y*width]` 会错位
- **验证**：查阅 JPEGENC 源码，确认 addMCU 的 (x,y) 含义
- **改动**：按正确语义计算像素偏移

### H5：条纹周期与 JPEG MCU（8x8）对齐

- **假设**：条纹若为 8 像素周期，可能与 JPEG 8x8 块边界重合
- **验证**：输出 raw 灰度图（不 JPEG），或改用 PNG/其他格式；若条纹消失则与 JPEG 相关
- **改动**：临时绕过 JPEG，直接发送 raw 小图（需改协议或仅本地调试）

1. **一次一假设**：每次只改一个变量，便于归因
2. **最小改动**：优先加调试输出，再考虑改渲染逻辑
3. **验证命令**：`run_optical_pipeline.sh --mode with-model ... --capture-seconds 20 --no-clean`
4. **记录**：每轮写入本 plan 的「调试记录」小节

## 4. 建议首轮尝试（H2：固定 scale）

- **理由**：实现简单，可快速排除 per-frame 归一化影响
- **改动**：在 `flow_render_to_gray` 中，用固定 scale 代替 `mag/max_mag`：
  - 例如 `v = mag * 80.0f`（或根据 out_scale 调），`v = min(255, v)`
  - 观察条纹是否减弱、是否出现「挥手区域明显变亮」
- **实现**：增加 `FLOW_VIZ_FIXED_SCALE` 宏，为 1 时走固定 scale 路径

## 5. 调试记录

### R1：用户反馈（2026-02-23）

- **现象**：条纹仍存在；挥手时黑线随挥手频率闪动，延迟低
- **结论**：flow 对运动有响应，链路正常；条纹来源待定位
- **下一步**：优先尝试 H2（固定 scale）

### R2：H2 固定 scale 实现（2026-02-23）

- **改动**：`flow_render.cpp` 增加 `FLOW_VIZ_FIXED_SCALE=1`，用 `mag * 80` 代替 `mag/max_mag`
- **验证命令**：`run_optical_pipeline.sh --mode with-model --app-type optical_cam_oflow --port /dev/ttyACM0 --capture-seconds 20 --model-arg '...' --no-clean`
- **用户反馈**：条纹整体变亮，其他没变；条纹仍存在；有一点点动态反馈。

### R3：H1 列均值诊断实现（2026-02-23）

- **改动**：`ob_debug_stats` 增加 `ob_log_col_mean_mag_sample()`，每 8 列一个采样，输出该列 mean magnitude（×1000）
- **验证**：烧录后观察串口 `[col_mean_mag]` 行，若 c0,c8,c16,... 呈交替高低模式，则条纹来自 flow 数据周期；若较平则可能为 JPEG 或 H3/H4
- **结果**：列均值较平坦（3876–4105），无周期 → H1 排除，指向 H5/H4

### R4：H5 尝试1 - JPEG_Q_BEST（2026-02-23）

- **改动**：`flow_render.cpp` 将 `JPEG_Q_HIGH` 改为 `JPEG_Q_BEST`（最高质量）
- **验证**：烧录后 Windows 端观察条纹是否减轻
- **用户反馈**：还是条纹，无明显改善。
- **结论**：H5 尝试1 排除；条纹非 JPEG 压缩质量导致。

### R5：H4 代码语义审查（2026-02-23）

- **分析**：阅读了 `library/JPEGENC/jpeg.inl` 源码，`JPEGENCODE` 中的 `cx` 和 `cy` 实为 MCU 的像素尺寸（如 8x8 或 16x16）。外层循环在累加时 `jpe.x += jpe.cx`，因此 `jpe.x` 和 `jpe.y` 确实是绝对的像素坐标。
- **计算**：在 `flow_render.cpp` 中 `&gray[jpe.x + jpe.y * width]` 传给 `addMCU` 且 `iPitch=width`，这与内部 `pSrc += iPitch` 的每次跳行完全匹配。
- **结论**：H4 排除。`gray` 到 `JPEG` 的内存交接和跨度步长逻辑是正确的。条纹并非来自于 MCU 拼装错位。

## 6. 下一步执行计划（H5测试图与H1高频采样）

经过 H4 和 H5-尝试1 排除，当前「内存渲染管线」和「JPEG编码器」本身出现 Bug 的概率降低，焦点重回「数据本身（H1）」或「Web 端/浏览器 JPEG 渲染色彩空间识别偏差」。

### 动作 1：植入纯几何测试图（Test Pattern）以隔离 Web 端与数据源

我们无法确定条纹是来自于 `flow_data` 还是上位机的展示偏差。只需强制生成一个简单的灰度渐变图作为 `flow_data` 的替身。
- **做法**：在 `flow_render_to_gray` 函数内增加 `#if FLOW_VIZ_TEST_PATTERN`，忽略模型 flow 输入，强制向 `out_gray` 填充 `out_gray[y * out_w + x] = (uint8_t)(x % 256)` 或固定纯色。
- **预期**：
  - 如果在 Himax Web 端看到的是平滑渐变或整齐图案，说明后链路（JPEG+串口+Web）**完美无瑕**，条纹 100% 来自于模型的 `flow_data` 输出内容本身。
  - 如果连这个测试图也有条纹，说明后链路有问题（可能当成 Raw rgb565 等了）。

### 动作 2：密集取样替代低频采样（修复 H1 验证漏洞）

之前的 `ob_log_col_mean_mag_sample(..., step=8)` 可能中了奈奎斯特采样定律的陷阱：如果条纹周期恰好是 2, 4, 或者 8 个像素，步长为 8 的采样就会完全对齐同一个相位，导致输出数值显得异常平坦。
- **做法**：修改 `ob_log_col_mean_mag_sample`，改为取连续前 16 列的均值（即 c0, c1, c2 ... c15），而不是步进取样。同时可以多打印一个区域如 `c100 - c115`，以便直接肉眼阅读数据是否存在奇偶跳变或周期波浪。

### 动作 3：确认 TFLite Layout 维度（H3 兜底）

- 之前的解析日志为 `model io: in(h=150,w=200,c=6) out(h=160,w=208,c=2)`，显然维度末尾 `c=2` 符合标准的 NHWC layout。但在 TOSA 或者 Ethos 转换时，可能在 NHWC 下暗藏 NCHW 的实质填充模式。
- 如果「动作 1」证明 Web 显示无误，而「动作 2」显示数据有高频周期，我们将尝试改变 `flow_render.cpp` 中取 `mag` 的方式（例如跨越 `W*H` 作为偏移读取通道），验证 H3。

### 即将生成的代码修改：
1. `cvapp_yolov8n_ob.cpp` 或 `ob_debug_stats` 更新列采样算法（步长改1，观测连续16列）。
2. `flow_render.cpp` 引入 `FLOW_VIZ_TEST_PATTERN`，拦截赋值为渐变图。
3. 把这些变动写好后，通过 `run_optical_pipeline.sh` 进行验证，并发 Discord 通知让 Windows 端的用户做实验并给予反馈。

## 7. 执行结果与破案结论（2026-02-23）

我们在最新的固件中推入了两个重要的修改：
1. **拦截渲染，强制生成平滑渐变图案** (`FLOW_VIZ_TEST_PATTERN=1`)
2. **修改采样方式为 `step=1` 的连续密集列采样**

### 测试现象极具突破性！
在串口日志中，我们抓取到了修改 `step=1` 后的真实数据状态特征（取自 `sram_test_modified_vela.tflite`）：

- `c4, c5, c6, c7` / `c12, c13, c14, c15`: ~2000-2400（低）

### 最终破案结论：
1. **源数据本就带条纹！** H1 假说（模型输出或 Ethos-U 显存中的原始数据存在奇偶空间混叠或棋盘格伪影）被 100% 证实！
2. **为什么我们之前瞎了？** 因为之前的版本为了避免日志太多，`step=8` 的采样步长**正好完美踩中了这个 8 像素的波动周期**（如 c0, c8, c16 ... 或 c2, c10, c18 ...），导致每次采样都在同一相位（比如全被读到了 `3334` 或者 `4000`），从而完美掩盖了这股剧烈的高频振荡！
3. **JPEG 和内存渲染完全无辜**：我们证实 JPEG MCU 拼接和压缩算法没有做错任何事。H4 / H5 并未引发此问题，条纹完全是 `flow_data` 喂进来的毒数据。
