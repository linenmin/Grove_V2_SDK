# 第二阶段搜索空间设计现状说明

## 1. 这份文档是干什么的

这份文档用于让一个完全没有前提知识的新 agent 快速理解当前情况，并继续设计第二阶段搜索空间。

它只回答五件事：

1. 第一阶段搜索空间是什么。
2. 当前最重要的固定骨架是什么。
3. 当前固定骨架对应的 `arch code` 是什么。
4. 第二阶段已经明确要改什么。
5. 第二阶段还有哪些问题没有定论。

---

## 2. 当前任务的核心目标

当前模型是一个**光流估计模型**。

它的任务是：

- 输入两帧图像
- 预测从前一帧到后一帧的像素运动

在当前实现里，可以把输入理解为：

- 两帧 RGB 图像按通道拼接后的输入
- 因此输入通道数是 `6`

模型不是单尺度输出，而是一个多尺度 decoder：

- 会产生 `/4`
- `/2`
- `/1`

三个尺度的预测 head。

在训练配置中，基础光流通道数是 `2`，因为要预测二维光流；当前训练还使用 uncertainty 相关设置，因此实际 head 输出通道数会扩展，不等于纯粹的 2 通道 flow。

当前不是单纯追求最高 accuracy，而是在部署约束下提升 accuracy。

最重要的三个指标是：

- `SRAM peak`
- `FPS`
- `accuracy`

当前阶段的核心要求是：

- 不突破当前可部署的 `SRAM peak`
- 不明显拖慢 `FPS`
- 在这个前提下尽量提升 accuracy

---

## 3. 第一阶段搜索空间是什么

第一阶段的 supernet 使用 9 维 `arch code`。

这 9 个位置分别是：

| arch code 位置 | 模块 |
| --- | --- |
| 1 | `EB0` |
| 2 | `EB1` |
| 3 | `DB0` |
| 4 | `DB1` |
| 5 | `H0Out` |
| 6 | `H1` |
| 7 | `H1Out` |
| 8 | `H2` |
| 9 | `H2Out` |

其中分成两类 choice block。

### 3.1 Backbone 的 4 个 choice block

这 4 个位置是：

- `EB0`
- `EB1`
- `DB0`
- `DB1`

它们共享同一套候选：

| choice 值 | 含义 |
| --- | --- |
| `0` | 1 个 residual block |
| `1` | 2 个 residual block |
| `2` | 3 个 residual block |

### 3.2 Head 的 5 个 choice block

这 5 个位置是：

- `H0Out`
- `H1`
- `H1Out`
- `H2`
- `H2Out`

它们共享同一套候选：

| choice 值 | 含义 |
| --- | --- |
| `0` | `3x3` |
| `1` | `5x5` |
| `2` | `7x7` |

---

## 4. 第一阶段哪些层不是搜索对象

下面这些在第一阶段是固定的，不属于 `arch code`：

- `E0`
- `E1`
- `Down1Conv`
- `Down2Conv`
- `Up1`
- `Up2`

其中最重要的是：

- `E0` 固定为 `7x7` stride-2 conv
- `E1` 固定为 `5x5` stride-2 conv

这也是为什么第二阶段现在会专门讨论“是否把前两层纳入搜索”。

---

## 5. 当前最重要的固定骨架：`globalgate4x_bneckeca`

第二阶段搜索空间讨论时，当前最重要的参考骨架不是原始 supernet，而是 `globalgate4x_bneckeca`。

它可以理解为：

- 第一阶段同一套 backbone/head 主体
- 加上两个固定增强模块

这两个增强模块是：

1. `bottleneck ECA`
2. `/4 global gate`

### 5.1 它的主干顺序

当前 `globalgate4x_bneckeca` 的结构顺序是：

1. `E0`
2. `E1`
3. `EB0`
4. `Down1Conv`
5. `EB1`
6. `Down2Conv`
7. `DB0`
8. `eca_bottleneck`
9. `Up1`
10. `DB1`
11. `Up2`
12. `global_gate_4x`
13. `H0Out`
14. `H1`
15. `H1Out`
16. `H2`
17. `H2Out`

### 5.2 `bottleneck ECA` 的真实含义

这里的 `ECA` 不是抽象概念，而是一条具体算子链：

1. `reduce_mean`
2. `reshape`
3. `Conv2D(1x3, filters=1)`
4. `reshape`
5. `sigmoid`
6. `multiply`

它的位置是：

- 在 `DB0` 后面

### 5.3 `/4 global gate` 的真实含义

`global_gate_4x` 的逻辑是：

1. 对 bottleneck feature 做全局平均
2. 用 `1x1 conv` 投影到目标通道数
3. 经过 `sigmoid`
4. 对 `/4` decoder feature 做逐通道缩放

它的位置是：

- 在 `Up2` 后面，也就是 decoder `/4` 位置

---

## 6. 当前固定骨架对应的 `arch code`

当前最常用的固定 `arch code` 是：

- `0,2,1,1,0,0,0,0,0`

逐位解释如下：

| 位置 | 模块 | 当前值 | 含义 |
| --- | --- | --- | --- |
| 1 | `EB0` | `0` | 1 个 residual block |
| 2 | `EB1` | `2` | 3 个 residual block |
| 3 | `DB0` | `1` | 2 个 residual block |
| 4 | `DB1` | `1` | 2 个 residual block |
| 5 | `H0Out` | `0` | `3x3` |
| 6 | `H1` | `0` | `resize + 3x3` |
| 7 | `H1Out` | `0` | `3x3` |
| 8 | `H2` | `0` | `resize + 3x3` |
| 9 | `H2Out` | `0` | `3x3` |

这个结果至少说明一件重要的事：

- 当前固定骨架里，5 个 head 位置最后都落在了最小 kernel，也就是 `3x3`

---

## 7. 当前已经明确的结论

这一节只写已经明确的、和第二阶段搜索空间直接相关的内容。

### 7.1 第一阶段的 9 个搜索位置要保留

当前的意图不是推翻第一阶段搜索空间，而是：

- 保留原来的 9 个 `arch code` 位置
- 在此基础上继续扩展

### 7.2 第二阶段要把前两层也纳入搜索

当前已经明确希望把：

- `E0`
- `E1`

也纳入搜索空间。

这意味着第二阶段的 `arch code` 不再是 9 维，而应扩展为 11 维。

### 7.3 Head 部分要去掉 `7x7`

当前已经明确的判断是：

- head 部分的 `7x7` 几乎没有带来明显有效的 accuracy 提升
- 但会明显拖累 `FPS`

因此第二阶段 head 的搜索候选中：

- `7x7` 应该移除

这是当前最明确、最直接的搜索空间收缩结论。

---

## 8. 第二阶段搜索空间，最自然的 11 个位置

如果保留原来 9 个位置，并新增 `E0 / E1`，那么第二阶段最自然的编码顺序是：

| 新位置序号 | 模块 |
| --- | --- |
| 1 | `E0` |
| 2 | `E1` |
| 3 | `EB0` |
| 4 | `EB1` |
| 5 | `DB0` |
| 6 | `DB1` |
| 7 | `H0Out` |
| 8 | `H1` |
| 9 | `H1Out` |
| 10 | `H2` |
| 11 | `H2Out` |

这只是一个清晰的设计建议，不代表仓库里已经实现了 11 维版本。

## 9. 第二阶段目前还没有定论的问题

这部分非常关键。下面这些问题现在还没有定，不应被当成既定事实。

### 9.1 `E0 / E1` 的候选到底怎么定义

当前已经明确的是：

- `E0 / E1` 要纳入搜索

但还没有定的是：

- 它们是继续做 kernel size 搜索
- 还是做更复杂的 stem block 搜索
- 是否引入 dilation

### 9.2 如果引入 dilation，顺序怎么放

当前没有定论的是：

- 先做空洞卷积，再做下采样
- 还是先做下采样，再做空洞卷积
- 还是把 dilation 设计成另一条独立候选分支

这件事现在必须留给后续 agent 分析，不能写成结论。

### 9.3 第二阶段是否仍然保持所有位置都是 3 选

当前很多现有训练和统计逻辑默认：

- 每个位置只能取 `0 / 1 / 2`

但第二阶段如果：

- `E0 / E1` 用一套新候选
- head 去掉 `7x7`

那么就需要重新决定：

- 是继续强行做成统一 3 选
- 还是允许不同类型位置有不同候选数

这件事目前也没有定论。

### 9.4 第二阶段是否以 `globalgate4x_bneckeca` 作为固定 scaffold

这很可能是自然方向，但目前还没有正式实现成“第二阶段 supernet 的既定基础”。

因此它现在只能看作一个强相关方向，不能写成已完成事实。

---

## 10. 给下一位 agent 的最短接班结论

如果只看这一节，也应该能接上工作。

### 已确定的事实

1. 第一阶段 `arch code` 长度是 `9`。
2. 前 4 位是 backbone deep choice。
3. 后 5 位是 head kernel choice。
4. 第一阶段 `E0 / E1` 不可搜索。
5. 当前重要固定骨架是 `globalgate4x_bneckeca`。
6. 它是在原骨架上加入：
   - bottleneck ECA
   - `/4 global gate`
7. 当前常用固定 `arch code` 是：
   - `0,2,1,1,0,0,0,0,0`
8. 第二阶段希望保留原来的 9 个搜索位置。
9. 第二阶段希望新增：
   - `E0`
   - `E1`
10. 第二阶段 head 部分要去掉 `7x7`。

### 未确定的问题

1. `E0 / E1` 候选具体长什么样。
2. 是否引入 dilation。
3. 如果引入 dilation，具体顺序怎么设计。
4. 第二阶段是否继续保持所有位置统一 3 选。
5. 第二阶段是否正式以 `globalgate4x_bneckeca` 为 supernet scaffold。

这五个问题需要后续 agent 自己分析，不应直接继承成结论。
